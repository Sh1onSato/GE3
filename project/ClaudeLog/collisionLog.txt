# 当たり判定 試行錯誤ログ (collisionLog.txt)

このファイルは、当たり判定の実装内容、テスト結果、および今後の課題を記録する専用メモです。
開発中の「なぜこうしたのか」「何が起きたのか」を蓄積し、より高度な物理挙動を目指します。

## 1. [2026/06/10] 初期実装：球 vs AABB と スライディング・コリジョン

### 採用した手法
- **判定形状**: プレイヤー（球体 / 半径0.5） vs 壁（AABB / 軸に沿った直方体）
- **移動処理**: スライディング・コリジョン（軸別判定方式）

### なぜこの手法にしたのか？
- **計算負荷の低さ**: FPSにおいて最も頻繁に行われる「壁との接触」を高速に処理するため。
- **操作性の向上**: 壁に斜めにぶつかった際、移動を完全に止めずに「壁に沿って滑る」挙動（FPSの標準的な操作感）を実現するため。

### 試行結果
- **良好な点**: 
    - 壁を突き抜けることなく、スムーズに外周や障害物を歩けるようになった。
    - X軸とZ軸を独立して計算することで、角に引っかかるストレスが軽減された。
- **調整した数値**:
    - `playerRadius = 0.5f`: プレイヤーの体格。大きすぎると狭い場所を通れず、小さすぎると壁にめり込んで見えるため、モデルのスケールに合わせてこの値に設定。

### 今後の懸念点と可能性
- **トンネル現象 (Tunneling)**:
    - 非常に薄い壁を作ったり、移動速度を極端に上げたりした場合、判定を「飛び越えて」突き抜ける可能性がある。
    - **対策案**: 連続的衝突判定（CCD）の導入（移動前の点と移動後の点を結ぶ「線」で判定する）。
- **多重衝突**:
    - 角（2枚の壁が重なる場所）で同時に判定が起きた際、押し出しが競合してガクつく可能性がある。
- **段差の乗り越え**:
    - 現状は足元に少しでも壁があると「壁」として止まってしまう。
    - **対策案**: 一定の高さ（30cmなど）以下の衝突は無視して、座標を上に持ち上げる「ステップアップ処理」の追加。

## 2. [2026/06/10] 重力とジャンプの実装

### 採用した手法
- **重力処理**: 毎フレーム一定の加速度（`kGravity = -0.008f`）を `velocity.y` に加算。
- **床判定**: Y軸の移動後に衝突判定を行い、衝突していて且つ `velocity.y < 0`（落下中）であれば接地（`isOnGround = true`）とみなす。

### 試行結果
- **良好な点**: 
    - 壁だけでなく、床（floor）の上でも正しく止まるようになった。
    - 空中でのジャンプを禁止し、着地してから再度跳ぶという自然な挙動が実現できた。
- **課題**:
    - **頭打ち**: ジャンプ中に天井にぶつかった際、頭がめり込んで一瞬止まるような挙動になる。
    - **坂道/階段**: 現在の判定では「少しの段差」も壁として扱われるため、スムーズに登ることができない。

## 3. [2026/06/10] 足元基準の座標系と床抜け対策

### 課題：カメラ中心判定の限界
- 以前はカメラ位置を判定の中心にしていたため、しゃがみ処理（半径を小さくする）を行うと、中心点が地面に近づきすぎて床を突き抜ける不具合が発生した。

### 解決策：playerPos（足元）と EyeHeight（目線）の分離
- **playerPos**: 常に「足元」が地面に接するように移動・判定を行う。
- **EyeHeight**: 表示用のカメラは `playerPos` から一定距離（1.5ユニットなど）だけ上にオフセットさせて配置する。
- **床の厚み**: 判定を安定させるため、床モデルのスケールを `1.0` に増やし、上面を `0.0` に合わせた。

### 試行結果
- **良好な点**: 
    - 目線の高さを自由に変えても、接地判定が不安定にならなくなった。
    - 床の下に吸い込まれるような現象が完全に解消された。

## 5. [2026/07/01] レイキャストの面法線計算（ヒットエフェクトの向き改善）

### 課題
- `Calculation::TestRayAABB` は交点(`hitPoint`)は返すが、法線を `{0,0,0}` に固定していた（簡略化のため）。
- そのため火花の飛散方向を「弾の入射方向の逆向き(-D)」で代用しており、壁に浅い角度で当てると火花が壁にめり込む向きに飛んで不自然だった。

### 採用した手法（スラブ法の副産物で法線を得る）
- スラブ交差法で `tmin` を更新した軸(X/Y/Z)と、その軸のレイ進行方向の符号を記録。
- 入射面の外向き法線は「レイ進行方向と逆側の面」＝ 進行が正なら min 側の面(法線 -1)、負なら max 側の面(法線 +1)。追加コストはほぼゼロ。
- レイ始点がAABB内部などで軸が確定しない場合は入射方向の逆向きで代用（安全策）。

### 火花方向のブレンド（GameScene::FireShot）
- 火花中心 = 正規化(`面法線` ＋ `-D` × `kSparkBackBias`)。
- 「面法線」だけだと地面で真上への噴水になり不自然。`-D`（撃った方向の逆＝手前へ戻る向き）をブレンドすることで、着弾点から手前へ跳ね返るFPSらしい挙動になった。
- `kSparkBackBias`（既定1.0）で寄せ具合を調整：0で法線のみ、大きいほど撃った側へ強く戻る。

### 試行結果 / 今後
- 壁の斜め・端に当てても火花が面にめり込まず、手前へ散るようになった。ビルド通過。
- 特異点（法線が +Z / -Z と平行なケース）は、次工程の弾痕デカール実装で「+Z→法線」回転を作る際にガードが必要（メモ）。

## 6. [2026/07/28] ポータル設置レイキャストが「見えない遮蔽物」を貫通する不具合

### 症状
- ボス（[[boss-fight-milestone]]、1v1ボス戦フェーズ2で追加）に照準を合わせてポータル設置ボタンを押すと、画面上には何も設置されないのに、2回目の設置操作を受け付けなくなる（内部的には設置済み扱いになっている）現象をユーザーが発見。

### 原因
- `GameScene::PlacePortal()`のレイキャスト対象(`targets`)は「床・壁のみ」（`FireShot()`とは別に独自のリストを持つ設計、[[プロジェクトの区切り目標|boss-fight-milestone]]参照）。ボスがこのリストに含まれていなかったため、プレイヤーがボスに照準を合わせても光線はボスを素通りし、ボスの奥にある壁まで到達して「命中」判定になっていた。
- 結果、ポータルはボスの真後ろ（プレイヤーの視点からはボスの体に完全に隠れる位置）に実際には設置されており、`portal.isPlaced = true`は正しくセットされる。見た目には何も起きていないように見えるが、内部状態は「設置済み」になるため、次の設置操作（同じボタン）が`!portal.isPlaced`ガードで弾かれ、「設置できないのに設置した判定になる」ように見えていた。
- **教訓**：新しいObject3d（今回はボス）を追加する際は、`FireShot()`のような「実際に当てるレイキャスト」だけでなく、`PlacePortal()`のような「視線が通るかどうかを判定する別系統のレイキャスト」にも遮蔽物として含める必要がないか確認すること。的(`EnemyTarget`)や壁のように「実体があって視線を遮るもの」を新規追加するたびに、既存のレイキャスト系統（現状は`FireShot`用と`PlacePortal`用の2系統）を横並びで洗い出すのが安全。

### 対応
- `PlacePortal()`の`targets`にボスを追加してレイキャストの遮蔽物として機能させつつ、`RaycastClosest()`の`outObject`引数（`FireShot`側では既に使っていたが`PlacePortal`側では未使用だった）を受け取り、命中オブジェクトがボスだった場合はその場でreturnして「設置面としては扱わない」ようにした。これでボスに照準を合わせた場合は「奥の壁を貫通してしまう」ことなく、正しく「設置されない」（`isPlaced`もfalseのまま）状態になる。
- ユーザー確認済み（「よさそう」）。

## 7. [2026/07/28] ボスAI移動の障害物回避が複数回の試行でも解決せず（未解決のまま一旦中断）

### 経緯
1v1ボス戦ロードマップの第3フェーズ「ボスAI移動」（[[boss-fight-milestone]]参照）で、ボスが常にプレイヤーへ向かって歩くチェイスAIを実装。プレイヤーの`playerPos`/`CheckCollision`と同じ仕組みを流用し、`CheckCollision`に半径引数(`radius`)を追加してボス用の当たり判定（`kBossCollisionRadius=2.0`）に対応した。しかし、障害物（壁・中央カバー・角プラットフォーム）に対する回避行動で以下の順に問題が発覚し、複数回修正を試みたが最終的にユーザーから「まだよくならない」との報告があり、解決しないまま一旦中断した。

### 試行1：X/Z軸個別のスライディングコリジョン（プレイヤーと全く同じ方式）
- 単純にX軸移動→Z軸移動を別々に試す方式にしたところ、ユーザーから「壁際でプレイヤーがボスを追い詰めると、はめごろしのように動けなくなる」と指摘。

### 試行2：完全に行き詰まった時だけ左右90度へ回り込む
- `!movedX && !movedZ`（X/Z両方とも移動できなかった時）を検知して、進行方向に対し垂直な方向へ回り込む処理を追加。
- **問題発覚**：プレイヤーとボスがほぼ一直線（例：Z方向のみに差がある）に並んでいる場合、X軸は「動こうとした量がほぼ0だから障害物が無くても常に成功扱い」になり、`movedX=true`が常に成り立ってしまう。そのため実際にはZ軸が完全に塞がれていても「両方失敗」判定が発動せず、回り込みが機能しなかった。
- → 判定基準を「軸ごとの成功可否」から「意図した移動量に対する実移動量の割合（3割未満なら行き詰まりとみなす）」に変更。

### 試行3：回り込み方向をコミット式に（毎フレーム判定し直さず一定時間維持）
- 角の際どい位置で毎フレーム「回り込み成功/失敗」が入れ替わり、ガクガクと振動する不具合が発覚（ユーザー報告：「角に引っかかって振動(ガクガク)する」）。
- `bossAvoidTimer`（`kBossAvoidCommitDuration=0.4秒`）を追加し、回り込みを始めたら一定時間は同じ方向を保持するよう変更（`cameraShakeTimer`等と同じ「一定時間状態を保持する」パターンを踏襲）。

### 試行4：左右交互切り替え＋後退フォールバック
- スクリーンショットで、ボスが木箱の陰の位置から完全に動かなくなる不具合が発覚。原因は「回り込む方向をプレイヤーとの位置関係だけで毎回同じ計算式で決めていた」ため、その側がたまたま塞がっている袋小路（コーナー platform等）では永久に同じ（塞がった）方向を選び続けてしまうこと。
- `bossStuckCycles`で連続失敗回数を数え、2回目以降は前回と逆側を試す「左右交互」に変更。それでも`kBossStuckCyclesBeforeRetreat=3`回連続で失敗したら、プレイヤーの逆方向へ後退する`bossRetreating`フォールバックを追加。

### 試行5：衝突面の法線を使ったスライディング（ユーザー提案）
- ユーザーから「最短距離を直進しようとしているのが原因では。当たっている方向以外に進むようにできないか」との指摘。
- `CheckCollision`に`outPushDir`引数を追加し、衝突した障害物のうち最も近い（めり込みが深い）ものについて「最近接点→球の中心」への正規化ベクトル（衝突面の法線）を返せるようにした。
- ボスの移動ロジックを簡素化：直進を試し、衝突したら直進方向から法線成分を除去（平面へ射影）した「壁沿いの方向」へスライドする、物理的に素直な方式に全面書き換え。これに伴い試行3・4で追加した`bossAvoidSign`/`bossAvoidTimer`/`bossStuckCycles`/`bossRetreating`は不要になり削除。
- **結果**：ユーザーから「まだよくならないけど一旦ここまで」との報告。改善したかどうか含め未検証・未解決のまま次回に持ち越し。

### 現状・次回への申し送り
- ボスの直進チェイス自体（障害物が無い時に追いかけてくる基本動作）は問題ない。障害物を回避しながら追跡を継続する部分だけが未解決。
- 試行5（法線スライディング）はまだ改善が確認できていない。考えられる未検証の原因：
    - `CheckCollision`は単一のY高さ（`bossPos.y + kBossCollisionRadius`）でしか判定しておらず、ボスの実際の高さ(0〜5)の一部しか見ていない。角プラットフォームのような複雑な形状では、判定に使うY位置によって「当たっている」はずの面を見逃していないか要確認。
    - スライド後の位置も`CheckCollision`で再チェックしているが、それすら失敗した場合は何も動かない（その場で停止）ままになる。実際にどの状況で止まっているか、ImGui等でボスの位置・pushDir・distanceをリアルタイム表示してデバッグする方が次回は効率的かもしれない。
    - `kBossCollisionRadius=2.0`はボスの見た目のスケールと同じ値だが、球近似のため角では実際の箱形状より判定が小さく（＝めり込みやすく）なる。逆に面同士では正しく機能するはずなので、具体的にどの障害物・どの位置で止まるかを再現条件として次回確認したい。

## 8. [2026/07/29] ボスAI移動の障害物回避 解決（試行6：衝突継続中は方向固定＋詰み時のみ単一方向後退）

### 経緯
本項目7番で中断していた試行5（衝突面法線でその場スライド、毎フレーム再計算）を、ユーザー提案「一度衝突が起きたら、衝突している間は方向を再計算しない方がスムーズなのでは」を起点に見直した。

### 採用した手法
- `bossAvoiding`/`bossAvoidDir`を追加。直進が塞がった**最初のフレームだけ**`pushDir`（衝突面法線）から滑り方向を計算してキャッシュし、以後は直進が再び通るまで同じ方向を使い続ける（試行5の「毎フレーム再計算」をやめた）。
- ただし単純にキャッシュするだけだと、キャッシュした方向自体が別の障害物（角の隣の面など）に塞がれた場合、恒久的に詰む重大な退行が発覚（ユーザー報告：プレイヤーが動いても二度と動かなくなった）。**キャッシュした方向での移動が失敗したら、その場でキャッシュを破棄して次フレーム再計算に戻す**よう修正して解消（成功して滑れている間だけキャッシュを維持する設計に確定）。
- さらに「動けなかったフレームが続く」ケース（木箱の角＋壁で完全に囲まれ、直進・スライドどちらも毎フレーム失敗し続ける詰み）への対策として、`bossStuckTimer`（0.3秒）を追加し、一定時間動けなかったら**プレイヤーから離れる方向（真後ろ1方向）へ後退**を試みるフォールバックを追加。

### 試したが不採用だったもの：後退方向の5方向探索
- 単一方向の後退だけでは、その後退方向自体が壁で塞がれた袋小路（本項目7番で報告されたケースと同型）で後退も失敗し続ける事例が発覚（ユーザー報告：後退も発動しなかった）。
- 対策として後退方向を「真後ろ・135°・-135°・90°・-90°」の5方向を順に試す方式に拡張したが、**ユーザー評価は「変わらず詰まるし、むしろ止まる頻度が増えた」で悪化**。
- 原因調査で、脱出成功パスに`bossMoved = true`/`bossStuckTimer = 0.0f`のリセット漏れバグを発見（脱出後も「詰み」扱いのままになり、以後毎フレーム通常の直進・スライドを試さずこの探索だけが動き続けて迷走していた）。バグ自体は修正したが、5方向探索という方式自体をユーザーが「前の方（単一方向後退）がいい」と判断したため、**単一方向後退＋上記バグ修正のみを残す形に戻して確定**。
- **教訓**：詰み検出のフォールバックには「成功時の状態リセット」を必ずセットで実装すること（`bossMoved`のような「今フレーム動けたか」を表すフラグは、通常経路だけでなくフォールバック経路の成功時にも必ず更新する）。忘れると「一度発動したら二度と通常経路に戻らない」という別種の詰みを生む。

### 結果
ユーザー確認により「ほぼ問題ないレベルで解決（次フェーズへ進める）」と判断。1v1ボス戦ロードマップは次フェーズ「ボス攻撃」へ進める。

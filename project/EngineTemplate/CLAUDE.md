# プロジェクト概要

（ここにゲーム固有の概要を書く。例: 「DirectX12を使った自作エンジンベースの◯◯ゲーム」）
C++20、Visual Studio環境。本エンジンはGE3プロジェクトから切り出した自作DirectX12エンジンを基礎としている（詳細はREADME.md参照）。

## 基本動作ルール
- **会話は常に日本語で行う**
- コード変更は差分（変更箇所のみ）で提示する。ファイル全体の再出力は明示的に求められた場合のみ
- 実装前に `/plan` で方針を確認してから着手する（大きな変更の場合）
- **ビルド・コンパイルは自分で実行しない。必ずユーザー側で行う**
- ビルドエラーが発生した場合はユーザーがエラーログを貼る。原因特定と修正差分の提示のみ行う

## トークン消費を抑える運用ルール
- ファイルは全文Readせず、`Grep`で該当箇所を特定してから必要な範囲だけ読む
- 広範なコードベース探索（複数ファイルにまたがる調査）は`Explore`サブエージェントに委任し、要約のみを受け取る
- 規模の大きい実装作業やビルドエラー調査もサブエージェントに切り出し、結論・差分のみを会話に反映する
- **サブエージェント委任の閾値**: 単一ファイル・小規模差分（目安30行未満）は直接編集する。複数ファイルにまたがる実装や新機能追加のみサブエージェントに委任する（些細な修正での委任は起動オーバーヘッドの方が大きい）
- **対象ファイルが判明している場合はExploreを使わない**: ユーザーがファイル名・クラス名を指定した場合はGrep/Readで直接調査する。Exploreは実装箇所が不明な広範探索の時のみ使う
- **確認・質問はまとめて1回で行う**: 曖昧な点が複数あっても往復せず一度にまとめて聞く
- **ドキュメント追記は区切りごとに1回にまとめる**: codeLog/collisionLog/project.txtへの追記は、1回の実装完了ごとに1回だけ行い、途中で何度も書き直さない
- **大規模な新機能は`/plan`でフェーズ分割し、フェーズごとにユーザーのビルド確認を挟んでから次に進む**（ビルドは必ずユーザー側で行う運用のため、一気に全部実装すると原因特定が困難な不具合を積み上げるリスクがある）

## アーキテクチャ（エンジン側・汎用）
- **Framework** → WinApp / DirectXCommon / SrvManager / ImGuiManager / AudioManager を所有・一元管理
- **描画**: Object3d(3D) / Sprite(2D) / ParticleManager(インスタンシング) / PostProcess(オフスクリーン) / Skybox
- **設計パターン**: Manager(保管) / Common(PSO・設定) / Standard Object(実体) の3階層
- **シーン管理**: SceneManager + Abstract Factory (SceneFactory)。新規シーンは`BaseScene`を継承し`SceneFactory::CreateScene()`に文字列キーで登録する
- **数学**: Calculation.h に行列・ベクトル・クォータニオン・当たり判定（レイキャスト、球vsAABB）を集約
- **入力**: キーボード・マウスに加えゲームパッド(XInput)対応
- **設定の永続化**: `GameSettings`（シーンをまたぐ値の置き場、プロセス内メモリのみ・ファイル永続化なし）
- **スケルタルアニメーション**: 自前JSON/glTFパーサ(`GltfLoader`)＋GPUスキニング(`Skeleton`/`Animation`/`SkinCluster`/`SkinnedObject3d`)。1メッシュ/1スキン/1アニメーションのみ対応、`.glb`非対応。簡易リグでのみ動作確認済み（README.md参照）

### 現時点でエンジンに無い機能（新規ゲームで必要なら都度実装する）
- glTFローダーの拡張（複数メッシュ/複数アニメーション/`.glb`/morph target）
- アニメーションブレンド・状態遷移
- 汎用当たり判定はレイキャスト・球vsAABBのみ（AABB-AABB等は無し）
- UIのクリック判定・汎用レイアウト
- レベルデータの外部ファイル化（配置は全てC++コードにハードコードする前提）
- `TextureManager`/`ModelManager`のリソースUnload（シーン往復が多いとVRAM蓄積に注意）
- セーブ/ロード（ファイル永続化）

## ドキュメントファイルの取り扱いルール

### ClaudeLog/codeLog.txt【追記のみ・削除禁止】
- 初心者でも理解できる取扱説明書。クラスの役割・関係性・使い方を詳しく解説したもの
- **既存の内容は絶対に削除・上書きしない**
- 新しいクラスや仕組みを追加実装した場合は、末尾に同じスタイル（初心者向けの丁寧な解説）で追記する
- **参照タイミングを限定する**: タスク開始時に自動的に読みに行かない。ユーザーが明示的に指示した時、または実装が一区切りついて追記を書くタイミングでのみ参照する

### ClaudeLog/collisionLog.txt【追記のみ・削除禁止】
- 当たり判定の試行錯誤の記録。「なぜこうしたか」「何が起きたか」を蓄積するメモ
- **既存の内容は絶対に削除・上書きしない**
- 当たり判定に関わる変更・実験の結果は末尾に追記する
- **参照タイミングを限定する**: タスク開始時に自動的に読みに行かない。ユーザーが明示的に指示した時、または当たり判定関連の変更が一区切りついて追記を書くタイミングでのみ参照する

### ClaudeLog/project.txt【自己判断で追記・修正可】
- 進捗管理ファイル。未完了タスクと解決済み課題を管理する
- 新機能の実装完了後は「解決済みの課題」セクションに自己判断で追記してよい
- 未完了タスクの状況更新も自己判断で行ってよい
- **参照タイミングを限定する**: タスク開始時に自動的に読みに行かない。ユーザーが進捗確認を指示した時、または実装完了後に状況を追記・更新するタイミングでのみ参照する

（フォルダ名「ClaudeLog」は元プロジェクトからの踏襲。気に入らなければ`DevLog`等に変えてよいが、変えたらこのファイル内の記述も揃えて直すこと）
